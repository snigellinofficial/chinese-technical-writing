# 中文写作规范

> 让模型写出的中文站得住：不编造否定，不自造术语，不跳过解释。

这是一套面向大语言模型的中文写作规则，用于约束模型生成的文档与对话答复。规则写成两个 Markdown 文件，放进客户端的技能目录即可生效；随附一个检查程序，可以对任意中文文档执行机械判定。

## 解决什么问题

模型生成的中文往往语气流畅，信息却站不住。常见的情况如下：

1. **虚假的否定。** 模型写出“这不是一个普通的工具，而是一个高效的工具”，而“普通工具”从未在任何地方出现过。读者被迫先接受一个并不存在的对照物。
2. **自造的术语。** 模型写出“落盘”“闭环”“抓手”，或者“对流程进行了赋能”。这类词看着专业，读者却无法确定它指什么。
3. **跳跃的解释。** 模型写出“退出码为 0，因此校验通过”，却不说明退出码是什么。读者需要自行补齐中间环节。
4. **包装语。** 模型在结论前加“值得注意的是”，在结尾加“希望对你有所帮助”。这类文字不承载信息，只增加阅读负担。

这四种毛病有一个共同点：它们都能通过语法检查，也都读起来通顺，因此只能靠写作规范来约束。

## 规则一览

规则分为六节，各节的作用如下：

| 节 | 作用 | 典型要求 |
|---|---|---|
| 否定审慎 | 阻断没有对象的否定 | 被否定之物必须真实出现过 |
| 高级词审慎 | 阻断自造术语 | 名词要能被读者从上下文理解 |
| 可理解性与结构化 | 阻断跳跃的行文 | 未出现过的名称要解释，引言要列出次序 |
| 书面用词 | 阻断口语与随意表达 | 动词用两字书面词，成分不压缩成短语陈列 |
| 编辑保真 | 保护原文信息 | “可能”不改“必然”，原文只谈潜力时不补实现方式 |
| 语言形式 | 规范标点与排版 | 汉字与半角字母之间加空格，单句不超过 40 字 |

其中编辑保真一节用于审稿与润色场景。多数文风指南只讲怎样写得好看，这一节另外规定了哪些信息不得改动。

## 对照示例

下表列举规则的实际效果。其中，左边是修改前的写法，右边是修改后的写法。

| 修改前 | 修改后 | 对应规则 |
|---|---|---|
| 值得注意的是，本轮完成了重试策略的调整 | 本轮调整了重试策略 | 删除包装语 |
| 这不是一个普通 skill，而是高效率的写作工具 | 我以 skill 的形式提供了一个提高写作效率的工具 | 否定审慎 |
| 校验脚本报告 0 处问题，退出码为 0 | 检查程序逐条扫描文件，返回的退出码为 0，表示检查通过 | 上下文解释 |
| 改动落盘完成，跑一遍校验即可 | 改动已经写入文件，执行一次检查即可 | 书面用词 |
| 句子的主语和宾语都写明了，没有压成短语陈列 | 该句子的主语和宾语都以明确的形式表示出，而没有被压缩为短语式的陈列 | 对象关系完整 |

## 安装

把 `SKILL.md` 与 `reference.md` 复制到客户端的技能目录即可。常见位置如下：

| 客户端 | 技能目录 |
|---|---|
| DSH | `~/.agents/skills/chinese-technical-writing/` |
| Claude Code | `~/.claude/skills/chinese-technical-writing/` |
| Codex | `~/.codex/skills/chinese-technical-writing/` |

```bash
git clone https://github.com/snigellinofficial/chinese-technical-writing.git
mkdir -p ~/.claude/skills/chinese-technical-writing
cp chinese-technical-writing/{SKILL.md,reference.md} ~/.claude/skills/chinese-technical-writing/
```

复制完成以后，会话的技能列表中会出现名为 `chinese-technical-writing` 的条目。模型在判断任务与中文写作相关时读取该文件。

如果希望规则在全部会话中无条件生效，可以把六节规则的核心条文抄进客户端的全局指令文件，例如 `~/.claude/CLAUDE.md` 或者 DSH 的 `AGENTS.md`。该文件的内容会随每个会话自动载入。

## 使用

规则无需调用，模型读取之后即按其写作。若要检查既有文档，运行随附的检查程序：

```bash
node scripts/check.mjs                     # 检查当前目录下的规则文件
node scripts/check.mjs docs/ README.md     # 检查指定的文件或目录
npm run check:all                          # 检查本项目的全部文档
```

程序只依赖 Node.js 标准库，无需安装依赖。它把判定结果分成两类：可以直接判定的问题计入退出码，需要人工核对的审计项单独列出。输出样例如下：

```text
检查文件：5 个
  SKILL.md
  reference.md
  README.md

可直接判定的问题：0 处

需要人工核对的审计项：27 处
SKILL.md:26: [如下用法] “如下”之后应当使用冒号并另起一段 —— 顺承关系应当使用说明词表示……
```

发现可以直接判定的问题时，程序以退出码 1 结束，因此可以直接接入持续集成：

```yaml
- name: 检查写作规范
  run: node scripts/check.mjs README.md docs/
```

## 设计取舍

与其他文风指南相比，这套规则有三点不同。

首先，它针对的是模型特有的毛病。错别字与标点错误早就有工具处理，而虚假的否定、自造的术语、跳跃的解释是模型生成文本的特征问题，需要专门的条文。

其次，它的规则可以逐步机械化。每条判据都写成可判定的形式，其中标点、字间距、套话、术语与引出语的结构已经由 `scripts/check.mjs` 覆盖，其余部分依靠输出之前的自检。

再次，它为改写场景保留了逆向条款。规则不只规定应当怎么写，也规定不得改动什么，例如情态、条件、责任主体与数字。用于润色他人稿件时，这一类条款比文风偏好更重要。

## 已知限制

检查程序覆盖规则中可机械判定的部分。句长、段落粒度、套话密度与逻辑连贯性无法可靠地由程序判定，仍然依靠人工核对，程序会把这类情形列为审计项。

`SKILL.md` 的体积受技能目录上限约束。多数客户端拒绝载入过大的技能文件，且不给出提示。如果载入之后技能没有出现在列表中，可以只保留前两节，把其余内容留在 `reference.md` 按需查阅。
