# 中文写作规范

一套面向大语言模型的中文写作规则，用于约束模型写出的文档与对话答复。规则写成两个 Markdown 文件，可以放进支持技能（skill）机制的客户端。

版本 0.1。规则正文约 400 条，随附一个检查程序。

## 这套规则解决什么问题

模型生成的中文往往语气流畅，信息却站不住。常见的情况如下：

第一种是虚假的否定。模型写出“这不是一个普通的工具，而是一个高效的工具”，而“普通工具”从未在任何地方出现过。读者被迫先接受一个并不存在的对照物。这套规则要求：写否定之前，先确认被否定的东西真实出现过；没有出现过，就改写成肯定陈述。

第二种是自造的术语。模型写出“落盘”“闭环”“抓手”，或者“该项目对流程进行了赋能”。这类词看着专业，读者却无法确定它指什么。这套规则要求：选用名词之前先确认读者能从上下文理解它，没有必要的生硬词一律换成朴实表述。

第三种是跳跃的解释。模型写出“退出码为 0，因此校验通过”，却不说明退出码是什么。这套规则要求：上下文中没有出现过的名称、程序名、状态码和文件路径，都要在首次使用时给出解释；输出要有引言与顺序，不得从结论直接跳到细节。

第四种是包装语。模型在结论前加“值得注意的是”，在结尾加“希望对你有帮助”。这类文字不承载信息。这套规则要求删除它们，并把并列信息写成编号列表或者“首先”“其次”“再次”。

## 规则举例

下表列举规则的对照效果。其中，左边是修改前的写法，右边是修改后的写法。

| 修改前 | 修改后 | 对应规则 |
|---|---|---|
| 值得注意的是，本轮完成了重试策略的调整 | 本轮调整了重试策略 | 删除包装语 |
| 这不是一个普通 skill，而是高效率的写作工具 | 我以 skill 的形式提供了一个提高写作效率的工具 | 否定审慎 |
| 校验脚本报告 0 处问题，退出码为 0 | 检查程序逐条扫描文件，返回的退出码为 0，表示检查通过 | 上下文解释 |
| 改动落盘完成，跑一遍校验即可 | 改动已经写入文件，执行一次检查即可 | 书面用词 |
| 句子的主语和宾语都写明了，没有压成短语陈列 | 该句子的主语和宾语都以明确的形式表示出，而没有被压缩为短语式的陈列 | 对象关系完整 |

## 安装

把 `SKILL.md` 与 `reference.md` 复制到客户端的技能目录即可。常见位置如下：

| 客户端 | 技能目录 |
|---|---|
| DSH | `~/.agents/skills/chinese-technical-writing/` |
| Claude Code | `~/.claude/skills/chinese-technical-writing/` |
| Codex | `~/.codex/skills/chinese-technical-writing/` |

复制完成以后，会话的技能列表中会出现名为 `chinese-technical-writing` 的条目。模型在判断任务与中文写作相关时读取该文件。

如果希望规则在全部会话中无条件生效，可以把四个最高优先级条文抄进客户端的全局指令文件，例如 `~/.claude/CLAUDE.md` 或者 DSH 的 `AGENTS.md`。该文件的正文会随每个会话自动载入。

## 使用

规则无需调用，模型读取之后即按其写作。若要检查既有文档，运行随附的检查程序。

```bash
node scripts/check.mjs                     # 检查当前目录下的规则文件
node scripts/check.mjs docs/ README.md     # 检查指定的文件或目录
```

程序只依赖 Node.js，无需安装依赖。它做两类检查：一类是可以直接判定的问题，例如汉字与字母之间缺少空格、标题末尾出现点号、使用 emoji；另一类是需要人工核对的审计项，例如否定表述、口语用词、自造术语。程序发现问题时以退出码 1 结束，可以直接接入持续集成。

```bash
# 示例：在提交前自动检查
node scripts/check.mjs && git commit -m "更新文档"
```

## 规则文件

| 文件 | 内容 |
|---|---|
| `SKILL.md` | 核心清单，共六节，供写作时直接参照 |
| `reference.md` | 逐条判据与正反示例，供核对细节 |
| `scripts/check.mjs` | 检查程序，可独立使用 |
| `DEVELOPMENT.md` | 打包约束、检查程序的实现要点与维护说明 |

`SKILL.md` 的六节依次是否定审慎、高级词审慎、可理解性与结构化、书面用词、编辑保真、语言形式。其中编辑保真一节规定改写他人原文时不得改动情态、条件与数字，用于审稿和润色场景。

## 这四条规则好用在哪里

首先，它抓住的是模型难以自查的问题。标点与空格可以由程序判定，而虚假的否定、自造的术语、跳跃的解释只能靠写作时的自觉。这套规则把这些要求写成了可对照的条文。

其次，它对改写场景有保护条款。多数风格指南只讲怎样写得好看，这套规则另外规定了哪些信息不得改动，例如“可能”不能改成“必然”，原文只谈潜力时不补实现方式。用于润色他人稿件时，这一点比文风要求更重要。

再次，它给出了可解释的示例。每条规则配正例与反例，反例放进围栏代码块，既便于人工核对，也避免检查程序把它判成违规。

## 已知限制

检查程序覆盖规则中可机械判定的部分。句长、段落粒度、套话密度与逻辑连贯性无法可靠地由程序判定，仍然依靠人工核对。

`SKILL.md` 的正文体积会受到技能目录上限的约束。若你的客户端拒绝载入该文件，可以只保留前两节，把其余内容留在 `reference.md` 中按需查阅。
