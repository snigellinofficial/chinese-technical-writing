# 中文写作规范

> 使模型生成的中文具有依据：不编造否定，不自造术语，不跳过解释。

本项目是一套面向大语言模型的中文写作规则，旨在约束模型生成的文字信息，使其真实、清晰和可读。项目 skill 的具体规则分为两个 Markdown 文件，置于客户端的技能目录即可生效；并随附一个检查程序，可以对任意中文文档执行机械判定。

## 解决什么问题

模型生成的中文往往语气流畅，信息却缺乏依据。常见的情况如下：

1. **虚假的否定。** 模型表述为“这不是一个普通的工具，而是一个高效的工具”，而“普通工具”从未在任何地方出现过。读者被迫先接受一个并不存在的对照物。
2. **自造的术语。** 模型使用“落盘”“闭环”“抓手”，或者“对流程进行了赋能”。这类词看似专业，读者却无法确定它所指的含义。
3. **跳跃的解释。** 模型表述为“退出码为 0，因此校验通过”，却未说明退出码的含义。读者需要自行补齐中间环节。
4. **包装语。** 模型在结论之前添加“值得注意的是”，在结尾添加“希望对你有所帮助”。这类文字不承载信息，仅增加阅读负担。

上述四个问题存在一个共同点，即四者都能通过语法检查，也都读起来通顺，因此只能依靠写作规范予以约束。

## 规则一览

规则分为六节，各节的作用如下：

| 节 | 作用 | 典型要求 |
|---|---|---|
| 否定与对比的审慎 | 阻断无对象的否定与无效对比 | 被否定之物必须真实出现过 |
| 高级词审慎 | 阻断自造术语 | 名词要能被读者从上下文理解 |
| 可理解性与结构化 | 阻断跳跃的行文 | 未出现过的名称要解释，引言要列出次序 |
| 书面用词与典雅 | 阻断口语与随意表达 | 动词用两字书面词，成分不压缩成短语陈列 |
| 编辑保真 | 保护原文信息 | “可能”不改“必然”，原文只谈潜力时不补实现方式 |
| 语言形式 | 规范标点与排版 | 汉字与半角字母之间加空格，单句不超过 40 字 |

编辑保真一节用于审稿与润色场景，其中规定了编辑过程中不得改动的信息，例如情态、条件、责任主体与数字。

下表列举规则的实际效果。其中，左边是修改前的写法，右边是修改后的写法。

| 修改前 | 修改后 | 对应规则 |
|---|---|---|

## 安装

把 `SKILL.md` 与 `reference.md` 复制到客户端的技能目录即可。常见位置如下：

| 客户端 | 技能目录 |
|---|---|
| DSH | `~/.agents/skills/chinese-technical-writing/` |
| Claude Code | `~/.claude/skills/chinese-technical-writing/` |
| Codex | `~/.codex/skills/chinese-technical-writing/` |

```bash
git clone https://github.com/snigellinofficial/chinese-technical-writing.git
mkdir -p ~/.claude/skills/chinese-technical-writing
cp chinese-technical-writing/{SKILL.md,reference.md} ~/.claude/skills/chinese-technical-writing/
```

复制完成以后，会话的技能列表中会出现名为 `chinese-technical-writing` 的条目。模型在判断任务与中文写作相关时读取该文件。

如果希望规则在全部会话中无条件生效，可以把六节规则的核心条文抄进客户端的全局指令文件，例如 `~/.claude/CLAUDE.md` 或者 DSH 的 `AGENTS.md`。该文件的内容会随每个会话自动载入。

## 使用

规则无需调用，模型读取之后即按其写作。若要检查既有文档，运行随附的检查程序：

```bash
node scripts/check.mjs                     # 检查当前目录下的规则文件
node scripts/check.mjs docs/ README.md     # 检查指定的文件或目录
npm run check:all                          # 检查本项目的全部文档
```

程序只依赖 Node.js 标准库，无需安装依赖。它把判定结果分成两类：可以直接判定的问题计入退出码，需要人工核对的审计项单独列出。输出样例如下：

```text
检查文件：5 个
  SKILL.md
  reference.md
  README.md

可直接判定的问题：0 处

需要人工核对的审计项：43 处
SKILL.md:28: [如下用法] “如下”之后应当使用冒号并另起一段，段首用顺序词或编号
  原文：顺承关系应当使用说明词表示……
```

发现可以直接判定的问题时，程序以退出码 1 结束，因此可以直接接入持续集成：

```yaml
- name: 检查写作规范
  run: node scripts/check.mjs README.md docs/
```

## 设计取舍

本项目有三项设计选择，分述如下。

第一项选择，是关于条文针对模型生成文本中的特征问题。其中虚假的否定、自造的术语与跳跃的解释列为重点判据，并为每一类问题配正例与反例。

第二项选择，是判据尽量采用可判定的形式。标点、字间距、套话、术语与引出语的结构，已经由 `scripts/check.mjs` 覆盖；其余部分依靠输出之前的自检。

第三项选择，是为编辑场景保留保护条款。规则既规定应当撰写的写法，也规定不得改动的信息，例如情态、条件、责任主体与数字；用于润色他人稿件时，这一类条款的优先级高于文风偏好。

## 规则实例

下表列举十项规则的实际改写。其中，原文取自 172 个历史会话的助手输出；改写之后是按规则处理的结果。原文已去除具体项目信息。

| 意见 | 原文 | 改写之后 |
|---|---|---|
| 不要出现无效否定与无效对比 | 这不只是抖动，而是通道当前不可用 | 该现象反映出通道当前不可用 |
| 不要出现评断性的恭维之词 | 很好，现在找到了核心文献 | 现已定位核心文献 |
| 不要出现生硬转折 | 这个办法笨但可靠 | 该办法虽然耗时较长，但结果可靠 |
| 修辞色彩词应当替换 | 新命名落入了既有规范 | 新命名属于既有规范 |
| 空洞动词与口语动词应当排除 | 这意味着省略是有意的 | 这表明省略是有意为之 |
| 虚词与句式模板应当规范 | 然后生成二维码，然后结束本轮 | 随后生成二维码，接着结束本轮 |
| 冒号不得用于解释 | 这是最明显的结构性问题之一：表格指向不存在的课文卡片 | 表格指向不存在的课文卡片，属于最明显的结构性问题之一 |
| 善用逗号与分号切分长句 | 引用第三方内容时注明出处全篇转载时在开头显著位置注明作者和出处并链接原文 | 引用第三方内容时，应注明出处；全篇转载时，应在开头显著位置注明作者和出处，并链接原文 |
| 主语与宾语不得随意省略 | 同步时把握两条原则 | 在文件指令同步的过程中，我应当同时把握两条原则 |
| 时态必须严格 | 我在规则中补上这条判据，再按新判据重写文档 | 我将在规则中补上这条判据，再按新判据重写文档 |

语料分布并不均匀。无效对比、空洞大词、名词短语冒号、口语虚词与长句未切分五类命中较多；评断性恭维、缩略化表达、主语省略与时态四类命中稀少。提取程序为 `scripts/sample-extract.mjs`，可以对任意语料重复运行。

## 已知限制

检查程序覆盖规则中可机械判定的部分。句长、段落粒度、套话密度与逻辑连贯性无法可靠地由程序判定，仍然依靠人工核对，程序会把这类情形列为审计项。

`SKILL.md` 的体积受技能目录上限约束。多数客户端拒绝载入过大的技能文件，且不给出提示。如果载入之后技能没有出现在列表中，可以只保留前两节，把其余内容留在 `reference.md` 按需查阅。
